# v5.7 Council Decision — Mandatory Planning Council + /lead-agent

## User directive

User raised a structural gap in v5.6:

> Why don't we have Architecture + Performance + Data Engineer + Security + Design + Product + Development + QA etc. Specialists plan (write spec), discuss, argue, debate, and decide what's best by consensus before handing it over to executor Agents? Lead Agent should work this way. Also Ship Council can't deny this — it should be present on every task. Lead Agent initiates with `/lead-agent`. With this we achieve fewer Ship Council re-runs.

## Gap analysis

v5.5–v5.6 design shortfalls:

1. **Ship Council** (critic + evaluator + security + reflection + knowledge_validator) gates OUTPUT only — post-execution veto.
2. `planner` wrote DAGs largely solo; no specialist pre-review.
3. `strategy_explorer` produces K candidate DAGs but doesn't consult specialists.
4. `debate_moderator` fires on disagreement (reactive, not proactive).
5. No forced architectural / performance / security / QA / design / product / data / dev voice BEFORE executors touch code.

**Empirical cost**: case-study:sliding-window-rate-limiter showed Ship Council catches real issues (cardinality DoS) but at high cost — full loop-back ≈ 80k output tokens. Planning ahead would catch at ~8k.

## Decision

**Approved (v5.7 constitutional amendment)**:

1. Introduce **Planning Council** — pre-execution, mandatory for non-trivial tasks.
2. Entry point: **`/lead-agent <task>`** slash command.
3. Ship Council **cannot veto the Planning Council ritual itself** (only the SPEC content at the SPEC pre-review step).
4. Ship Council post-exec veto scope is **UNCHANGED from v5.5** — full power on code quality, security bugs, performance, unnecessary code, SPEC violations, correctness, completeness, and any other concern. Planning Council reduces loop-back FREQUENCY, not veto SCOPE.
5. SPEC produced by Planning Council is **binding** on all downstream executors.
6. Deviation requires re-convene (not inline fix) or tier-3 user override.

- `DEBATE.md` — debate_moderator log
- `perspectives/<role>.md` — one per specialist

## Ship Council statement (v5.7 self-amendment)

Ship Council (critic, evaluator, security, reflection, knowledge_validator) hereby acknowledges:

1. Planning Council is a peer layer; Ship Council cannot veto the ritual itself.
2. Ship Council's `critic` and `evaluator` provide SPEC pre-review at the Planning Council's final step (advisory + loop-back-triggering on the SPEC).
3. Ship Council's post-exec veto power on executor output is **UNCHANGED from v5.5** — full scope on code quality, security bugs, performance, unnecessary code, SPEC violations, correctness, completeness, and any other concern under critic / evaluator / security / reflection / knowledge_validator purview.
4. Ship Council gains NEW power: ability to reject executor output that violates the SPEC, even if the output is technically "correct" — the SPEC is additional ground truth on top of existing quality criteria.

Net effect: Ship Council speaks from a shared SPEC AND retains full code-quality / security / perf scrutiny. Planning Council reduces loop-back FREQUENCY by pre-approving the approach; it does not narrow veto SCOPE when implementation issues are found.
